# Why are we here?

## I. Introduction

In the popular imagination, a designer is someone who comes up with ideas, produces a plan, and then hands it over to technicians to make real. The job, in this view, ends at the mock-up: thinking is ours, building is theirs. If that were true, a designer would have little reason to sit among developers, to open a code editor, or to care how a screen is actually constructed. So why are we here? Why should we, as designers, learn to code? This essay argues that coding is not a detour from design but a way of practicing it more fully. I will discuss the question from three angles: learning to code helps us communicate with developers so that designs can be implemented as intended; it helps us judge what is feasible, so that our proposals remain reasonable; and it enables us to build simple prototypes quickly, so that we can test our ideas before they go into production.

## II. Learning to Code Improves Communication with Developers and Helps Designs Get Implemented

I learned this not as a theory but as a game design intern working closely with programmers. In that role, a design was never a finished picture that could simply be handed off. Every proposal had to survive a conversation about how it would actually be built. If you knew nothing about code, those conversations were difficult in a very particular way. Developers would explain how your plan might be implemented, ask whether another approach could replace it because the current one could not be coded as drawn, and question details that were bound up with the technical system. This difficulty is not only personal. Maudet et al. (2017) found that designers and developers often work from different representations, producing “design breakdowns” in which missing details, overlooked edge cases, and ignored technical limits cause the product to drift from the original intent. Feng et al. (2023) likewise note that handing designs to developers remains difficult because of knowledge gaps and divergence between design and development. Without a shared language, you listen, you nod, and other people begin to fill in the blanks. Learning to code does not make the designer into a developer. It lets you stay in the conversation long enough to protect the design while it is being made real.

## III. Learning to Code Helps Designers Judge What Is Feasible and Makes Design More Reasonable

If you do not learn to code, you may design things that look brilliant on a board and still be impossible to build. I have seen how quickly a “perfect” idea can become a nightmare for programmers: a transition the engine cannot support, an effect that would destroy performance, a flow that assumes data the system does not have. The designer feels creative. The developer hears a request that makes them want to give up. This is not a rare accident. Babich (2022) notes that some designs look impressive precisely because they ignore whether developers can actually build them. Looking cool, he argues, does not make a solution feasible, and treating implementation as “the developer’s problem” is a serious mistake. Even basic coding skills help designers judge their own work from another angle. Stevens (2021) makes a similar point: there is often a gap between what the designer wants and what the developer can deliver, and designers who can “speak” frontend have a clearer sense of what is possible. Learning to code does not mean shrinking every idea to the safest option. It means catching the outrageous ones before they leave the studio, so that the design you propose is ambitious and still reasonable.
